# 代码注释清晰化设计

## 目标

为当前真实接线的代码补充简洁、准确的中文注释，让维护者能快速理解业务意图、权限边界、数据一致性约束和复杂状态流。本轮采用“关键处注释”标准，后续可逐步扩展到公共函数和组件级说明。

本轮不追求注释数量，也不逐行翻译代码。代码已经清楚表达的事实不再用注释重复。

## 范围

纳入：

- `notes-frontend/src`
- `notes-backend/src`
- 根目录及 `scripts` 中实际用于开发、部署或运维的关键脚本
- 测试文件中的复杂回归场景、特殊前置条件和不直观断言

不纳入：

- `node_modules`、构建产物和生成文件
- 普通 CRUD、直观 JSX 和自解释的工具函数
- 测试中的普通 arrange/act/assert 和直观断言
- 已废弃或没有真实调用方的脚本；这类内容应走删除流程，而不是补注释

## 注释标准

注释统一使用简洁中文，API 名、类型名、字段名和通用技术术语保留英文。

优先说明：

- 为什么采用当前实现，以及看似更简单的实现为什么不适用
- 谁可以读取、修改或删除数据，权限判断的单一真相源在哪里
- 多字段、多集合或异步任务之间如何保持数据一致
- 缓存失败、AI 调用失败、后台任务失败时如何降级
- 历史数据、第三方库或浏览器行为带来的兼容约束
- 协作编辑、搜索回退、分页和复杂 React 状态之间的关键时序
- 容易被未来维护者误删、合并或改错的不变量

禁止添加：

- 对 import、赋值、循环和简单条件的逐行翻译
- `检查用户`、`构造查询`、`返回结果` 等没有新增信息的标题式注释
- 与实现不一致的陈旧描述
- 大段背景故事、临时调试记录和没有对应约束的 TODO
- 为了提高覆盖率而添加的函数名复述

## 处理方式

采用风险分层方式，不要求每个文件都产生改动。

### 第一批：后端权限与数据一致性

检查 Notes、Semantic、Knowledge Base、Comments、Versions、Categories、Tags 等服务。重点标明 access scope、所有者与协作者权限、恢复或删除顺序、计数同步，以及跨集合更新的失败边界。

单一权限来源应明确指向 `NoteAccessService` 或所属领域服务，避免注释暗示调用方可以自行复制权限逻辑。

### 第二批：后端异步、缓存、搜索与 AI

检查派生摘要、embedding、推荐、缓存失效、keyword fallback、AI 响应规范化等路径。注释应说明同步结果与后台结果的关系、失败是否影响主请求，以及不同搜索模式的适用条件。

### 第三批：前端编辑器与协作状态

检查 `NoteEditorShell`、Tiptap、Markdown 编辑器、评论标记、协作者、白板和导图生命周期。重点说明初始化与销毁时序、受控/非受控状态边界、防止重复提交的机制，以及第三方编辑器桥接限制。

### 第四批：页面 hooks 与关键脚本

检查笔记列表、分类、搜索过滤、分页同步、登录注册和部署脚本。注释只覆盖跨状态协调、URL 同步、批量操作、部署前置条件和危险操作保护。

## 修改原则

- 先阅读完整职责和调用方，再写注释；不能仅凭局部代码猜测意图。
- 发现注释与代码冲突时，以验证后的行为为准，改写或删除旧注释。
- 允许将中英混用的关键注释统一为中文，但不做与目标无关的格式化。
- 注释任务原则上不改变运行时行为；若检查时发现 bug，单独记录并在获得授权后修复。
- 保留工作区已有改动，不覆盖、不回退、不混入无关注释。

## 验收标准

- 权限、数据一致性、缓存降级、异步任务、搜索回退和复杂 UI 时序均有必要的中文说明。
- 随机抽查注释时，注释能回答“为什么”或“有什么约束”，而不只是复述下一行代码。
- 不存在明显错误、过期或与实现矛盾的注释。
- 普通代码没有因机械注释而变得臃肿。
- TypeScript 类型检查、现有测试、生产构建和 `git diff --check` 通过。
- 注释改动按批次独立审阅；后续向函数/组件级说明扩展时沿用同一标准。

## 风险控制

最大风险是把推测写成事实。执行时必须结合调用链、测试和当前接线确认语义；无法确认的地方不写断言式注释，而是记录为待核实项。

第二个风险是注释很快失效。注释应贴近被约束的代码，并描述稳定的业务原因或不变量，避免记录容易变化的实现步骤。
