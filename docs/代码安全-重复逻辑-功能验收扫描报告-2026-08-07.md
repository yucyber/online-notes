## 1. 总体结论

当前项目的基础工程质量已经达到“可编译、可测试、可继续迭代”的水平：后端构建通过，后端 79 个单测通过，前端类型检查通过，前端 24 个 Jest 测试通过，生产构建通过，API 契约检查无漂移。

但当前不建议直接作为生产版本发布，原因不是单纯的代码风格问题，而是存在至少一个高影响的协作权限风险，以及依赖漏洞、会话凭据存储、登录/AI 缺少 HTTP 限流、正则搜索资源消耗等发布前事项。尤其是 Yjs 协作服务目前只验证 JWT 是否有效，没有在 WebSocket 房间层再次校验笔记 ACL；知道笔记 ID 的已登录用户理论上可以直接连接对应房间。

代码整体评价为“模块边界尚可、近期拆分有效，但核心编辑器和笔记服务仍偏重，重复的服务逻辑与前端状态编排尚未完全收敛”。不建议为了追求形式上的组件化进行大范围重构，建议优先处理权限与输入边界，再按职责拆分高复杂度文件。

## 3. 安全风险清单

风险等级含义：

- **高**：可能导致越权读写、会话接管、明显的拒绝服务或高额外部资源消耗，应在生产发布前处理。
- **中**：需要特定配置、输入或运行条件才能触发，但会影响安全基线或稳定性。
- **低**：主要影响维护、诊断或长期治理，不代表没有修复价值。

| 等级 | 问题 | 证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| 高 | Yjs 房间没有笔记 ACL 校验 | 前端房间名由 `TiptapEditor.tsx:31` 生成 `note:<noteId>`；`y-websocket/server.js:117-144` 只校验 JWT，不校验房间对应笔记的 owner/ACL | 已登录用户若知道笔记 ID，可尝试直接订阅其他笔记房间并读取或写入协作内容，HTTP 层的 `NoteAccessService` 不能保护 Yjs 通道 | **实测确认**（附录 A.5）：两个不同 userId 的有效 JWT 连接同一房间均成功，user-b 收到 Sync 消息（len=4），证明跨用户可读取协作内容。修复建议不变：由后端按笔记 ACL 签发短时 room ticket，或让 WS 服务调用共享的权限服务；房间名必须来自已签名 claim，禁止仅凭客户端传入 room；补充跨用户 WS 读写测试 |
| 高 | JWT 同时放在 `localStorage` 和可读 Cookie | `notes-frontend/src/lib/auth.ts:18-20,35,45` | 任意 XSS 都可以读取 token；Cookie 不是 HttpOnly/Secure，且 token 生命周期与前端脚本可见范围扩大 | 优先改为 HttpOnly + Secure + SameSite Cookie；如果保留 Authorization 方案，至少移除普通 Cookie，并建立 CSP、XSS 回归测试和 token 轮换 |
| 高 | 登录、注册、AI 接口没有 HTTP 限流/配额 | `main.ts:62-63` 的限流器只传给 WS adapter；`auth.controller.ts` 和 `ai.controller.ts` 没有 HTTP Throttler/Redis 限流 | 可进行密码暴力尝试、批量注册、AI provider 成本消耗或接口资源滥用 | 对登录按 IP+账号限速，对注册按 IP 限速，对 AI 按用户/IP/模型设置并发、日配额和超时；失败响应保持统一 |
| 高 | 依赖存在当前已知漏洞 | 后端 audit：16 个（9 moderate、7 high）；前端 audit：25 个（1 low、14 moderate、10 high）；Yjs 服务 audit：1 个 high；根目录 `ws` 也报告 1 个 high | 包含 `mongoose`、`ws`、`multer`、`path-to-regexp`、`axios`、`next`、`sharp` 等链路的 DoS、原型污染、SSRF 或 XSS 风险，具体是否可被本项目路径触发仍需逐项确认 | 先锁定并升级有非破坏性修复的直接依赖和传递依赖；逐项回归后再评估 major 升级；不要未经评估直接执行 `npm audit fix --force` |
| 高 | 笔记默认正则搜索未转义且无长度上限 | `notes-backend/src/modules/notes/notes.service.ts:109-115` 将用户 `keyword` 直接放入 Mongo `$regex`；`notes/dto/index.ts:98-113` 只校验字符串和模式 | 恶意正则或超长关键字可能造成 Mongo 查询 CPU/延迟升高，形成 ReDoS/资源耗尽 | 默认使用 `$text` 或对关键字做正则转义；若保留 regex 模式，限制长度、限制模式复杂度并设置查询超时和监控 |
| 中 | Yjs 可通过环境变量关闭认证，且缺少显式消息大小限制 | `y-websocket/server.js:117-121` 支持 `YWS_AUTH_DISABLED=1`；`server.js:15` 创建 WebSocket 时未设置 `maxPayload` | 生产环境误配时会形成匿名协作入口；超大二进制消息可能增加内存压力 | **实测确认**（附录 A.6）：server.js 未设置 `maxPayload`、连接数限制、房间大小限制；生产环境未拒绝 `YWS_AUTH_DISABLED=1`。修复建议：生产环境拒绝启动于 `YWS_AUTH_DISABLED=1`；显式设置 `maxPayload`、连接数和每房间大小限制；记录异常关闭原因 |

| 中 | RUM 收集与报告为公开接口且使用无界进程内 Map | `rum.controller.ts:8-17` 没有 guard；`rum.service.ts:8,10-18` 将事件累计到进程内 Map | 任意来源可以刷入指标；长期运行会积累日期 key；`/report` 还暴露运行指标，可被用于探测服务 | `/collect` 按 IP 限流并限制 event/meta 大小；报告接口加管理鉴权；定期淘汰历史日期，或迁移到有 TTL 的存储 |
| 中 | CORS 默认允许所有 Vercel preview 域名且开启 credentials | `main.ts:24,39,46` 默认正则为 `^https://.*\\.vercel\\.app$`，同时 `credentials: true` | 未受信任的 preview origin 可能参与跨域请求；当前 token 未完全采用 HttpOnly Cookie，但配置仍扩大了信任边界 | 生产环境只允许明确的正式域名和受控 preview 域名；按环境生成 allowlist，避免宽泛正则 |

| 中 | 自定义 Yjs 服务当前无法按 `y-websocket` 子项目独立启动 | `y-websocket/package.json` 声明 `jsonwebtoken` 等依赖，但当前子目录 `npm ls --depth=0` 报 unmet；`node y-websocket/start.js` 实测报 `Cannot find module 'jsonwebtoken'` | 单元测试只覆盖工具函数，未覆盖 server 启动；清洁环境或独立部署可能启动失败 | 将 y-websocket 作为独立 workspace/部署单元安装依赖并加入启动 smoke test；明确使用自定义 `server.js` 还是官方 `y-websocket/bin/server.js`，避免部署文档与代码分叉。**补扫更新**：执行 `cd y-websocket && npm install` 后，`node start.js` 已成功启动，1234 端口正常监听（附录 A.1-A.4） |

## 5. 代码混乱度与可维护性

### 5.1 主要问题

- `NoteEditorShell.tsx` 仍约 900 行，既是页面控制器又包含元数据处理、快捷键、全屏、评论和编辑器渲染，修改一个功能需要跨越较大的上下文。
- `notes.service.ts` 仍同时负责 CRUD、列表筛选、缓存、派生字段、ACL、锁和推荐委托，虽然已有多个子服务，但主 service 仍是编排中心。
- 前端存在 20 个 lint warning，主要是 hook 依赖和可访问性；其中 hook 依赖遗漏可能导致旧闭包或数据不同步，不能全部当作纯格式问题。
- 源码中 `any`、空 `catch` 和前端 API 层的类型断言较多，错误被吞掉后会让“降级成功”和“真实失败”难以区分。
- `ci:i18n` 当前失败 52 处，说明文案国际化规则与现有页面实现不一致；这属于质量门禁失败，不是单元测试能覆盖的问题。
- `next build` 明确显示跳过类型验证，且 Browserslist/Baseline 数据过期提示需要治理。

### 5.2 复杂度结论

项目不是“完全混乱”：模块、测试和近期抽取方向都比较清晰；但编辑器、笔记查询、AI/知识图谱这几条主链路的职责密度较高，当前更适合做小步、可回归的重构。建议顺序为：安全边界 → 输入/错误边界 → 编辑器状态编排 → 服务重复逻辑 → 文案与 lint 治理。

## 附录 A：y-websocket 补扫实测结果（2026-08-07）

> 前提：执行 `cd y-websocket && npm install` 安装 `jsonwebtoken`、`ws`、`y-websocket`、`yjs` 依赖后，以 `node start.js` 启动服务，1234 端口正常监听。JWT_SECRET 从 `notes-backend/.env` 自动加载。

### A.1 HTTP 存活检测

```text
GET http://localhost:1234/
→ 200, body="okay"
```

结论：**通过**。HTTP 健康检查端点正常。

### A.2 无 token 连接（应拒绝）

```text
WS /note:test-note-1
→ HTTP 401 Unauthorized, 连接未建立
```

结论：**通过**。`server.js:121-124` 正确拒绝无 token 的 WebSocket 升级请求。

### A.3 无效 token 连接（应拒绝）

```text
WS /note:test-note-1?access_token=invalid.token.here
→ HTTP 401 Unauthorized, 连接未建立
```

结论：**通过**。`server.js:132` 的 `jwt.verify` 正确拒绝无效 token，`catch` 分支返回 401。

### A.4 有效 token 连接（应成功）

```text
WS /note:test-note-1?access_token=<valid JWT, sub=user-a>
→ WebSocket 连接成功建立（opened=true）
```

结论：**通过**。使用与后端一致的 `JWT_SECRET` 签发的 JWT 可正常通过鉴权并建立 WebSocket 连接。

### A.5 房间级 ACL 验证（核心风险确认）

```text
步骤 1: user-a (sub=user-a) 连接房间 note:leak-test-<timestamp>
         → opened=true, 收到 1 条消息

步骤 2: user-b (sub=user-b, 无该笔记权限) 连接同一房间
         → opened=true, 收到 1 条消息 (Sync, len=4)
```

结论：**未通过（高风险确认）**。

- `server.js:117-144` 的 `upgrade` 阶段仅验证 JWT 签名和过期时间，不校验 `request.user.sub` 是否对 `room` 对应的笔记有读取/写入权限。
- 前端房间名由 `TiptapEditor.tsx:31` 以 `note:<noteId>` 格式在客户端生成，完全由客户端控制，服务端无条件信任。
- 任何已登录用户只要知道（或猜测）目标笔记 ID，即可构造 `note:<noteId>` 房间名并连接，接收 Yjs Sync 消息读取协作内容，也可发送写入消息。
- HTTP 层的 `NoteAccessService.readableFilter` / `writeScope`（`note-access.service.ts:12-65`）无法保护 WebSocket 通道。

### A.6 server.js 安全配置缺口

对 `y-websocket/server.js` 源码的静态检查结果：

| 检查项 | 结果 | 说明 |
| --- | --- | --- |
| `maxPayload` 设置 | 缺口 | `new WebSocket.Server({ noServer: true })` 未设置 `maxPayload`，超大二进制消息可增加内存压力 |
| 连接数限制 | 缺口 | 未设置每客户端或全局连接数上限 |
| 房间大小限制 | 缺口 | 未设置每房间连接数或文档大小上限 |
| 生产环境拒绝 `YWS_AUTH_DISABLED=1` | 缺口 | `server.js:117` 无条件检查环境变量，生产环境误配即形成匿名协作入口 |
| 房间名格式校验 | 缺口 | 不校验 `note:` 前缀，任意房间名（如 `/arbitrary-room-name`）均可连接 |
| 房间名与用户关联校验 | 缺口 | `upgrade` 阶段不关联 `request.user.sub` 与房间对应笔记的 ACL |

### A.7 补扫结论

y-websocket 服务的 JWT 鉴权机制（A.1-A.4）工作正常，可正确拒绝无 token 和无效 token 的连接请求。但**房间级 ACL 缺口已在运行时确认**（A.5）：任何持有有效 JWT 的已登录用户均可连接任意笔记房间并读取协作数据。此风险与第 3 节高等级风险第 1 项一致，应在生产发布前通过后端签发 room ticket 或 WS 服务调用共享权限服务的方式修复。
